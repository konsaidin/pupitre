# Slopsician — план (курс 2)

Вокальный тренажёр: поёшь в микрофон, приложение в реальном времени показывает
высоту тона, громкость и вокальные техники (вибрато, расщепление), сравнивает с
картой песни. Курс 1 (MVP: визард диапазона, пиано-ролл, упражнения, песни через
Demucs-пайплайн, Electron-десктоп) — реализован; этот план описывает курс 2.

## Приоритеты курса 2

1. **Низкая задержка звука** — от захвата до кадра детекции; замеряем и показываем.
2. **Универсальный аудиослой** — одинаковое поведение поверх драйверов
   Linux (PipeWire/ALSA), Windows (WASAPI), Android (AAudio/Oboe).
3. **Детекция вокальных техник** — вибрато, расщепление, громкость и всё,
   что читается нашим стеком без ML-моделей (jitter/shimmer, HNR, придыхание).
4. **Лента вокала** — главный вид вместо миди-пиано-ролла.

## Ключевые решения (зафиксированы 2026-07-15)

- **Визуализация — «лента-контур»:** голос рисуется непрерывной лентой;
  вертикальная позиция = высота тона, толщина = громкость, волнистость = вибрато,
  рваная текстура/цвет = расщепление. Целевая линия песни — тонкая направляющая
  под лентой, без клавиатуры. Пиано-ролл остаётся переключаемым вторичным видом.
  _Поправка 2026-07-17: по фидбеку пользователя дефолт для новых профилей —
  пиано-ролл (`profile.vocalView: 'roll'`); лента — переключателем в шапке._
- **Платформы — Capacitor + нативный звук:** текущий React-фронт один на всех;
  Android — Capacitor APK с Oboe-плагином, десктоп — Electron с нативным
  капчер-модулем, веб — AudioWorklet как fallback-путь.
- **DSP-ядро — Rust:** один код детекции компилируется в WASM (веб/Electron)
  и в .so через JNI (Android). Никакой дублирующей логики на Kotlin/JS.

## Архитектура

```
apps/web        — React/TS UI (грузится в браузер, Electron и Capacitor WebView)
apps/desktop    — Electron + нативный аудио-модуль (WASAPI/PipeWire)
apps/android    — Capacitor-обёртка + Oboe-плагин (новое)
packages/dsp    — Rust-ядро: f0 + техники → WASM + cdylib/JNI (новое)
services/api    — FastAPI: оффлайн-пайплайн песен (Demucs → карта) — без изменений
```

### Аудиослой: интерфейс AudioInput

Единственная точка входа звука для UI. Кадры анализа приходят уже готовыми —
DSP выполняется максимально близко к драйверу:

```ts
interface AudioInput {
  listDevices(): Promise<AudioDevice[]>;
  start(deviceId: string | null, opts: MicOptions): Promise<void>;
  stop(): void;
  onFrame(fn: (f: AnalysisFrame) => void): () => void;
  /** фактическая задержка тракта захват→кадр, мс — для калибровки и UI */
  latencyMs(): number;
}
```

Бэкенды:

| Платформа | Захват | Где крутится DSP |
|-----------|--------|------------------|
| Веб / fallback | getUserMedia + AudioWorklet | WASM внутри worklet |
| Electron Win | WASAPI (shared low-latency, опц. exclusive) | нативный поток, ядро как cdylib |
| Electron Linux | PipeWire (малый quantum) | нативный поток |
| Android | Oboe/AAudio (PerformanceMode::LowLatency, exclusive) | callback-поток, ядро через JNI |

Целевая задержка захват→кадр: **< 25 мс** нативно, **< 50 мс** в вебе.
Меряем реально (timestamp драйвера → выдача кадра) и показываем в настройках.

### DSP-ядро (packages/dsp, Rust)

Вход: моно-фреймы 48 кГц. Выход — `AnalysisFrame` каждые ~5 мс (hop 256):

```json
{
  "t": 12.345,
  "f0": 220.1, "midi": 57.02, "clarity": 0.91, "voiced": true,
  "loudDb": -18.2,
  "vibrato": { "active": true, "rateHz": 5.6, "depthCents": 42, "regularity": 0.8 },
  "distortion": { "active": false, "score": 0.1 },
  "breathiness": 0.2
}
```

Детекторы:

- **f0** — порт текущего YIN (CMNDF + параболическая интерполяция + анти-октава),
  дальше апгрейд до pYIN-подобной вероятностной оценки.
- **Два пути f0.** Сырой контур — для анализа техник; сглаженный (медиана+EMA,
  как сейчас) — только центр ленты. Текущее сглаживание в PitchTracker давит
  вибрато — детекция обязана работать ДО него.
- **Вибрато** — скользящее окно ~1 с по сырому f0: убрать тренд, автокорреляция /
  Гёрцель в полосе 4–8 Гц → частота, глубина в центах, регулярность.
  Активно: глубина ≥ 20 центов, ≥ 2 периодов подряд.
- **Расщепление** (drive/growl/rattle) — признаки без ML: субгармоники
  (энергия на f0/2, f0/3 — детектится удлинением периода в CMNDF), падение
  HNR, рост jitter/shimmer при стабильном f0. Score 0..1 + гистерезис.
- **Громкость** — RMS → dBFS с быстрым attack / медленным release (толщина ленты
  не должна мерцать); опционально A-взвешивание.
- **Придыхание** — HNR-канал, отдаём как число (визуализация — позже).
- Свежие детекторы добавляются в ядро, кадр расширяется — UI не переписывается.

### Лента вокала (VocalRibbon)

Canvas-компонент, замена PianoRoll как главного вида в игре, визарде и
упражнениях:

- Лента строится из истории `AnalysisFrame` (~последние 4 с): позиция —
  сглаженный midi, толщина — loudDb (лог-шкала на 4..24 px), волнистость —
  сырой f0 поверх центра при активном вибрато, рваные края + смена цвета —
  distortion.score.
- Целевая линия песни — направляющая под лентой; попадание подсвечивает
  сегмент направляющей (зелёный в допуске / серый мимо), допуски и октавная
  логика — как в текущем скоринге.
- Бейджи распознанных техник над лентой («вибрато 5.6 Гц», «расщепление»).
- Пиано-ролл — переключатель вида (настройка запоминается).
- 60 fps на слабом Android WebView: без React-перерендеров на кадр, один
  canvas, отрисовка из ring-буфера.

## Санация Windows-сборки и октавного отображения (2026-07-17)

Локальная кросс-сборка exe (electron-builder + wine, CI недоступен) вскрыла
цепочку из четырёх независимых багов. Контекст для продолжения в новой сессии.

### Симптомы

1. Десктоп под Wine: «Не удалось развернуть сервер обработки · uvicorn exited 3:
   OMP Error #179 GetNumaNodeProcessorMaskEx».
2. После отмены зависшего трека следующий вечно висел «в очереди».
3. Windows-сборка: «вместо вокала что угодно, но не он», пиано-ролл — мусор
   (у песен в meta.json `separated: false` — Demucs молча деградировал до
   анализа полного микса: мелодия из инструментов, «минусовка» = весь трек).
4. Везде (и в браузере): кружок голоса телепортируется на ±октаву, когда
   тянешь ноту вверх («порядок октав перепутан»). Чинилось трижды — не помогало.

### Причины и что сделано (код поправлен, exe пересобраны)

1. **OMP-краш** — libiomp5 (torch/MKL) зовёт GetNumaNodeProcessorMaskEx, под
   Wine это заглушка (ошибка 120) → abort. Фикс: `KMP_AFFINITY=disabled` в env
   uvicorn (`apps/desktop/backend.js`). На реальной Windows функция реализована.
2. **Смерть очереди** — DELETE песни во время обработки сносил каталог; пайплайн
   падал, а `save_meta` в except-обработчике кидала FileNotFoundError — исключение
   убивало единственный поток-воркер. Фикс: try/except вокруг тела воркера
   (`jobs.py`), `save_meta`/`load_meta` терпимы к удалённому каталогу (`store.py`),
   кооперативная отмена `SongDeleted` в progress-колбэке (`pipeline.py`). Смоук
   на реальном коде очереди прошёл.
3. **Тихая деградация Demucs** — истинная причина (найдена e2e под Wine, а не
   гипотезами): `demucs.audio.AudioFile` дёргает **ffprobe**, а в поставке
   бэкенда только `ffmpeg.exe` → WinError 2 → мгновенный отказ разделения →
   тихий фолбэк на полный микс. Фикс: mix.wav (он всегда stereo 44.1k после
   `decode_to_wav`) читается напрямую soundfile, AudioFile/ffprobe выброшены
   (`pipeline.py::separate_stems`). Сопутствующее: причина отказа теперь едет
   в meta (`SongMeta.separation_error` → API `separationError`) и показывается
   жёлтой строкой на карточке песни — тихой деградации больше нет. Плюс
   профилактика HF-кэша под Wine/Windows: `HF_HUB_DISABLE_SYMLINKS=1`,
   `HF_HUB_DISABLE_XET=1` в env uvicorn; битые 0-байтные snapshot-файлы с `?`
   в имени из кэша wine-префикса удалены (blobs при этом были целые — get_model
   работал, ложный след).
4. **cp1252 на Windows** — `write_text`/`read_text` без `encoding=` берут
   локальную кодировку: кириллица в названии песни, тегах или русском тексте
   ошибки роняла запись meta.json/map.json (`UnicodeEncodeError`) — песня
   вечно висела в processing, а до фикса очереди это же убивало воркер.
   Фикс: явный `encoding="utf-8"` во всём файловом IO (`store.py`,
   `pipeline.py`, `main.py`) + `PYTHONUTF8=1` в env uvicorn (backend.js) —
   закрывает и логирование, и IO сторонних библиотек.
5. **Октавные телепорты** — окончательное решение (после ЧЕТЫРЁХ починок
   display-fold, включая «принцип непрерывности» в этой же сессии): октавная
   поправка отображения **удалена полностью**. Точка/след на ролле — всегда
   сырой голос, ровно там, где поёшь; телепортов не существует по построению
   (engine.ts: displayMidi = f.midi; scoring.ts: display-fold функции
   выпилены). Прощение октавы на beginner/medium живёт только в скоринге
   (matchPitch) — визуально честно: поёшь октавой ниже цели — точка октавой
   ниже, но нота засчитывается. Урок: НЕ возвращать «умные» октавные поправки
   отображения — любая эвристика с перепривязкой даёт телепорты на живом
   голосе (микропаузы согласных/гейта = ложные онсеты).
6. **Октавные выбросы нот карты** («поётся в той же октаве, а ноты рандомно
   выше/ниже») — контурная `_fix_octave_flips` (A-B-A) пропускала срывы на
   краях фраз и целые фразы на субгармонике. Добавлен пост-проход
   `_fix_note_octaves` (pipeline.py), правила: (а) короткая (< 6 с) фраза на
   ~кратное октавы НИЖЕ регистра остальных нот И без фраз-компаньонов на своём
   уровне поднимается обратно — куплеты повторяются, субгармонический срыв
   одиночка (важно: критерий «±12 с малым остатком» без проверки одиночества
   ломал настоящие куплеты — у HIM контраст куплет/припев ≈ 11 полутонов!);
   (б) нота между согласными соседями на ~кратном октавы клеится к ним.
   **Свёртки применяются И к нотам, И к f0-контуру: полоска (pitchline) и
   ноты — один алгоритм по построению** (первая версия правила правила только
   ноты — линия «пела» в другой октаве; проверка после переснятия: 417 нот,
   0 рассинхронов полоска/ноты > 1.5 semi). Плюс окно ролла (`rollWindow`)
   держит все ноты строго внутри экрана (строка запаса вокруг крайних) — нот
   за экраном не бывает.

  2026-07-16) либо фильтр нот по доминирующему регистру с опорой на энергию.
  Пока смягчено: все ноты видны на экране (окно растягивается), в игре

## Архитектурные инварианты

1. Детекция техник читает **сырой** f0-контур; любое сглаживание — строго после.
2. Вся DSP-логика живёт в `packages/dsp`; платформенный код только захватывает
   звук и гоняет байты. Ни одного детектора на Kotlin/JS/C++.
3. UI потребляет только `AnalysisFrame` через `AudioInput`; прямых обращений к
   getUserMedia/worklet из экранов нет.
4. Кадры между потоками/мостами ходят батчами с таймстампами драйвера;
   таймстампы не пересчитываются в UI-время нигде, кроме одного места (движок).
5. Оффлайн-пайплайн (services/api) и формат карты меняются только аддитивно.

## Риски

- **Задержка WebView на Android** — детекция нативная (не страдает), но звук
  аккомпанемента из WebView может отставать; если заметно — вывод тоже через Oboe.
- **Расщепление без ML** — эвристики (субгармоники+HNR) могут путать с хрипом/
  шумом; закладываем score с гистерезисом и порогом в настройках; ML-классификатор
  (CNN на мел-спектре, onnx) — план Б, ядро уже отдаёт признаки.
- **Rust-тулчейн в CI** — wasm-pack + cross-компиляция JNI/N-API удлинит сборки;
  кэшировать, собирать ядро отдельным job.
- **Вибрато vs дрожь голоса** — порог регулярности; калибруем на реальных записях.
